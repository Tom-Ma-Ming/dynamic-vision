## 现有实际调用链

main.cpp 初始化配置、模型、设备，启动推理、PID、平滑、热键线程。

config.cpp:198 的 options::main_function：DXGI/GDI 采集 → Yolo::Type::V5 推理 → commit(frame).get() → mouse.fire(frame, boxes)。采集区域常量为 360×360，中心 (180,180)，见 include/dxgi-cap.h:23；不等于当前 320×320 模型输入/录像，也不等于仿真默认 640×480 场景。

mouse.cpp:375 的 fire：拆分 person/head → 首次选择最近候选 → 按中心距离和尺寸维持单目标 → 计算头部或兜底点 → EMA/固定 Y 规则 → 相对中心偏移与灵敏度换算 → Kalman 外推 → pid.submit_target。另有触发、设备端动作与 PC 冻结分支。

pid.cpp:79 的 submit_target 覆盖最新偏移并通知 PID 线程；move 计算增量、限幅后发布方向和剩余步数；smooth 分段执行；do_move 调串口或系统接口。serial_mouse.cpp:199 将增量序列化后写出。动作产生的新画面再由下一次采集观察，形成旧程序的外部反馈路径。

control_logic.cpp 中的纯函数适合参考，但运行路径并未调用其中的 calculate_pid_step、target_offset、choose_tracking_candidate，不能把这几个辅助函数的测试当成现行控制线程已验证。

## 迁移前必须处理的问题

| 优先级 | 源码证据 | 影响与接入要求 |
|---|---|---|
| P1 | mouse.cpp:388；config.cpp:5 | 旧类号 0=body/person、1=head；当前 0=head、1=person。必须在模型契约中显式转换，禁止直接互接类别整数。旧代码还把所有非 0 类都视为 head，适配器应拒绝未知类。 |
| P1 | mouse.cpp:400–432 | 旧兜底 y=person.top−0.4×height+4 假设头在身体框上方，与现在 person 包含 head 不兼容；例如 top=100、height=100 得到 y=64。新接口区分实际检测头点与几何估计点，采用框内归一化位置，歧义/不可信时拒绝或退回明确的身体目标点。 |
| P1 | kalman_tracker.cpp:105–140 | 状态转移使用秒制 dt，速度是坐标单位/秒；predict_ahead(frames) 却返回 p+v×frames。例：v=100、100 FPS、预测 1 帧应增加 1 个坐标单位，现公式增加 100。迁移时使用显式预测时刻/秒，包含观测年龄和预计执行延迟，不能照搬 latency_frames。当前 mot::Tracker::predictAt 已按纳秒转秒。 |
| P1 | pid.cpp:10–31；config.cpp:327；serial_mouse.cpp:134–160 | born_us_ 是可覆盖的“最近帧”时刻，没有随具体命令绑定；统计在发送调用前结束，不包含写入等待、设备执行和画面反馈。>=31 ms 的直方图又合并到一个桶。不能据此标定完整闭环 P95/P99；需要 command_id/frame_id 贯穿采样、生成、发送、应用、反馈各时点。 |
| P1 | pid.cpp:153–158、192–208 | 多个 atomic 字段并不组成一致命令快照。消费者读取旧剩余步数后，生产者可发布新命令，消费者随后 fetch_sub 会扣到新命令；方向/余数也可能跨代混合。仿真执行器应有单一状态所有者、带序号的完整命令以及明确的替换/取消规则。 |
| P1 | pid.cpp:108–149、229–240 | move 解锁后操作 PID 积分/历史状态，refresh 仅持 data_mutex_ 修改同一批非 atomic 状态；该锁不能保护锁外运算。filter_reset_ 只有置位没有消费，不能保证重置后的微分无尖峰。未来控制器由一个线程/确定性事件循环持有状态，重置也作为事件处理。 |
| P2 | mouse.cpp:655–698；pid.cpp:113–147 | EMA、固定 Y、灵敏度、按 10 ms 归一化的 PID 和 Y 比例系数均是旧经验参数；灵敏度换算后的单位也不是原图 px。需要独立命名、记录并消融；不能直接导入旧增益后宣称已标定。 |

旧引擎通过 V5 解码入口运行，当前是 YOLO11n 的既定输出契约；复用控制思路不意味着旧模型加载与解码可直接替代当前 TensorRT 后端。

## 当前仿真与完整视觉闭环的差距

当前 simulator.cpp:185–214 根据世界状态直接生成带噪检测框，复用 MOT；320–338 行用固定帧延迟的绝对目标点队列移动 aim。它能验证跟踪和受限执行器误差，但不是旧 PID 的分段增量执行模型，也没有执行动作改变下一帧投影再经 YOLO 检测的链路。CameraPan 是预设运动，未由控制输出驱动。

因此要分别交付两种证据：

1. **控制算法仿真**：确定性时钟、合成观测、相对增量执行器及反馈，用于定位延迟、量化、饱和和 PID 稳定性问题。
2. **视觉闭环集成**：自建场景渲染图像 → 当前 YOLO/TensorRT → MOT → 控制器 → 仿真执行器 → 更新场景/视角 → 渲染下一帧。真实录像作为离线感知回归，不会响应新控制命令，不能单凭录像回放宣称此环已闭合。

## 下一阶段接口草案（待实现）

- Observation：frame_id、capture_ts_ns、ready_ts_ns、图像尺寸/坐标变换、类别契约、检测列表。媒体时间、模拟时间、真实单调时钟分开标识，不直接相减。
- TargetState：明确选择的 track_id、状态时刻、原图 px 位置与 px/s 速度、协方差、头部点来源/可信度；沿用现有生命周期与歧义门控。
- ControlCommand：command_id、来源 frame_id/track_id、生成时刻、有效期、控制代号、相对执行单位增量。原图 px 到执行单位经过显式标定；不假定鼠标计数等于像素。
- SimActuator：单一命令消费方；模拟传输延迟/抖动、分段周期、量化余数、速率/加速度限制、失败与反馈。旧命令替换/失效有计数，取消后按明确事件顺序停止。
- Feedback：命令实际应用时刻、应用量、生成新观察的时刻。仿真真值只供场景推进和评分，控制器只能收到允许的观察/反馈，不能偷读未来真实延迟。

建议实施顺序：先建立上述接口和独立的相对增量执行器，保留现有绝对点执行器作为对照；再引入可配置、按秒计时的 PID；随后增加变化延迟/抖动与视角反馈；最后接通场景渲染到真实检测器。前两步完成不等于最后一步完成。

## 验收场景

- 类号倒置、未知类、320/360/640 尺寸与 letterbox 坐标恢复；person 包含 head、缺头、多个头候选时的明确行为。
- 恒速目标在 5/10/33 ms 观测间隔下以秒外推；0/10/30/80 ms 延迟，固定种子抖动、乱序、过期结果；不得提前应用命令。
- 新命令到达旧命令分段执行中途、取消、目标 ID 失效/变化、发布失败；不混代、不重复、不扣减新代旧步骤。
- 小误差量化、限幅、换向、长暂停、急停/变向、短遮挡；记录完整窗口误差、过冲、稳定时间、失败恢复和命令丢弃数。
- 同输入/同 seed 重复一致；无补偿、固定延迟补偿、估计延迟补偿使用相同场景与预先固定阈值。不得用真实未来应用时刻给待验证的控制器作弊。
- 视觉闭环需证明一条命令实际改变下一次渲染/检测结果，且可以按 frame_id/command_id 追溯全部阶段；单独报告检测和控制失败。

上述为下一阶段设计及测试入口，没有将旧设备发送代码复制进当前项目。本轮已有镜头补偿测试结论仍见 camera-motion-experiment.md；本评审不构成旧程序的运行或硬件性能验收。
